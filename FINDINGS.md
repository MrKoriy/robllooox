### Что работает (проверено на живом процессе)

1. **Кэш главного потока.** `confirmed_main_thread()` валидирует закэшированный
   L (G=[L+0x30], [G+0x88]==L, backref [[L+0x30]]==G, glue [L+0x78]!=0) и не
   запускает повторный скан. Первый поиск ~10 с (8 проходов), повторные exec —
   мгновенно. GBEST-лог сжат до смены лидера (было ~2700 строк/вызов).

2. **`lua_newthread` 0x102c529f0** — корутина создаётся корректно
   (tt=10, stack=sa+0x10, top==base, ci==base_ci). ВАЖНО: glue `[L+0x78]` у
   свежей корутины NULL (newthread его не копирует — копируются только
   [+0x70] и байты +4/+5). 

3. **`lua_resume` 0x102c48ab0** — сигнатура `(L, from, nargs)` ПОДТВЕРЖДЕНА
   дизассемблом: status-байт на `L+3` (YIELD=1, BREAK=6, свежая = 0 при
   ci==base_ci на `L+0x50` vs base_ci на `L+0x68`), nCcalls halfword `L+8`
   копируется из `from`, `from=NULL` легален. Roblox-обёртка зовёт колбэки
   `[G+0x528]`/`[G+0x558]` (thread enter/exit) вокруг запуска. Передаём
   `from = main` как делает внутриигровой coroutine.resume.

4. **SEGV 0x0 при resume от 13:13 объяснён (наиболее вероятно):** байткод в том
   тесте был от другой версии клиента → перемапленные опкоды → dispatch по
   невалидной entry таблицы = прыжок на 0. Механика resume не при чём.

5. **TValue-теги:** функция = **8** (проверено в luaD_call: `ldr w8,[func+0xc];
   cmp #8`), строка = 6, тред = 10 (byte0 у объекта — tt у GC-объектов в
   байте 0, статус треда — байт +3).

6. **`luaS_newlstr` (intern) 0x102c535b8** — `(L, char*, len) → TString*`
   (tt=6, hash@+4, len@+0x14, data@+0x18). Работает off-thread.

7. **Загрузчик байткода 0x102c5b648** (`bufload`): `(L, chunkname, bc, len,
   env)` — ТОЛЬКО байткод: entry (0x102c5b764) читает первый байт буфера и
   ветвится по версиям; исходник ("r"=0x72) уходит в ERRSYNTAX(3). Рабочая
   пара к нему — **0x101533bec** `(L, container*, chunkname_cstr, 0, 0)` —
   принимает refcounted-контейнер компилятора (`x0 = arg+8`, резолвер строки
   0x102991a18, данные TString с +0x18).

8. **std::string ABI Roblox** (alternate libc++ layout, снят с
   `std::string::__init` 0x10000c740): short — data[0x17], длина в байте
   +0x17; long — `{data@+0, size@+8, cap|1<<63@+0x10}`, байт +0x17 =
   `0x80|len&0x7f`.

9. **Компилятор найден и вызывается:** `0x103da7de0` — обёртка
   `compile(const std::string&) → контейнер` (sret через x8, исходник в x0;
   вызвать можно голым asm — НЕ C++-кастом: неявный dtor → неразрешённый
   символ → краш). Цепочка: 0x103da7de0 → 0x103da7b50 → 0x1029918a8 →
   0x102991910 → вариант A 0x102991cc8 (при флагах [0x1074c00e0]==1 и
   [0x1074bfec0]==1) / вариант B 0x102991e04, контекст-синглтон в
   [0x1071ebfd0]. Вызов проходит БЕЗ падений и исключений (lldb-трейс
   подтвержает полный проход до вариантов), НО контейнер приходит с
   исходником вместо байткода → loader отдаёт ERRSYNTAX(3) с "[string ...]".

### Как обновлять сигнатуры под новую версию клиента

1. `python3 tools/find_luau.py` — регенерирует `luau_signatures.h` по
   строковым константам Luau (stack overflow / bad argument / ...).
2. `python3 tools/xref_string.py /Applications/Roblox.app/Contents/MacOS/RobloxPlayer "<строка>"` —
   найти функцию по её строковой константе.
3. Сверить магию на местах вызова (LLVM-objdump):
   `xcrun -f llvm-objdump; llvm-objdump -d --start-address=A --stop-address=B RobloxPlayer`
   контрольные точки: cbz/b.ne гейта loadstring (0x101541310/31c),
   `mov w0,#0` геттера (0x10153530c), tt-сравнение `cmp w8,#8` в luaD_call
   (0x102c67f60).
4. Смещения lua_State, пережившие 0.732→0.735 без изменений: G@+0x30,
   stack@+0x38/0x40, ci@+0x50, top@+0x58, base_ci@+0x68, glue@+0x78,
   G->mainthread@+0x88. TValue: value@+0, tt(u32)@+0xc, размер 0x10.

4. **Скан по свежим корутинам слеп к долгоживущей игровой VM**: её корутины

## Что РАБОТАЕТ (верифицировано, без хардкода/галлюцинаций)

1. **Инжект стабилен.** `payload.dylib` грузится в живой RobloxPlayer (через
   `DYLD_INSERT_LIBRARIES`), поднимает IPC-сервер `/tmp/inj_ipc_<uid>.sock`,
   выполняет ванильный Lua (liblua 5.4 из Homebrew как fallback). Процесс не
   падает. (pkill -9 нужен — Roblox игнорирует SIGTERM; single-instance handoff
   убивает второй инстанс, запускать только на чистом столе.)

2. **RTTI → vtable → экземпляры ScriptContext — полностью работает:**
   - RTTI-имя `N3RBX13ScriptContextE` есть в бинаре (7 вхождений, verified).
   - Нужна маска по младшим 36 битам (`PTR_MASK 0xFFFFFFFFF`) — arm64e хранит
     указатели в const-данных с chained-fixup метаданными/PAC в старших битах.
     Точное сравнение `==` НЕ матчится.
   - Искать xref надо по ВСЕМ файловым секциям (через walk Mach-O load
     commands), а не по двум названным — typeinfo лежит в секции, отличной от
     `__cstring`/`__TEXT,__const`.
   - typeinfo = `ptr_to_name - 8`; vtable_data = `ptr_to_typeinfo + 8`.
   - Экземпляры ищутся сканированием RW-регионов (через `mach_vm_read_overwrite`,
     НЕ прямым чтением — иначе SIGSEGV на гонках unmapping).
   - Результат: 5–8 живых экземпляров `RBX::ScriptContext` стабильно.

3. **lldb attach работает** к adhoc-подписанному клиенту (`process load` dylib,
   `memory read`). Использовать для ручной проверки структур.

## Что НЕ получилось (честно)

- **lua_State НЕ находится в первых 0x400 байтах ScriptContext** простым
  указателем. Объект по `ScriptContext+0x110` — стабильная Roblox-структура
  (та же форма в разных прогонах), но НЕ vanilla lua_State: `+0x08` там
  указатель, а не `tt`-байт. Ложный матч по `byte[8]==8`.
- Backref-валидатор (L.global.mainthread == L) корректен, но ни один tt==8
  кандидат из ScriptContext его не прошёл — значит настоящего main thread
  нет в зоне прямого скана, он вложен глубже (shared_ptr control block,
  Engine-обёртка, отдельный аллокатор) или лежит вообще в другой структуре.

## Stage 3 pivot — что сделано (верифицировано)

**Офлайн signature extractor `tools/find_luau.py`** — без Ghidra/IDA, без
живого процесса, всё из реальных байт файла. Принцип: ищет характерные
строки Luau (ошибки) → ADRP-xref к странице строки → walk-back к прологу
(строгий: `stp x29,x30,[sp,#-N]!` + `pacibsp`).

Найденные и runtime-верифицированные функции (адреса link-time, версия
0.732.0.7321040; слайд = image_base − 0x100000000):

| функция (гипотеза) | link vmaddr | сигнатура (16 байт) |
|---|---|---|
| luaD_growstack ("stack overflow") | 0x100219bb0 | fd7b17a9 fdc30591 f40300aa e80700f9 |
| luaG_typeerror/runerror ("attempt to X") | 0x101846108 | fd7b03a9 fdc30091 c00200b4 f40303aa |
| luaL_argerror ("bad argument") | 0x10179d510 | fd7b04a9 fd030191 e20800b4 f40301aa |
| lua_resume-ish ("cannot resume") | 0x100256270 | fd7b01a9 fd430091 488103b0 08e10e91 |

Прологи верифицированы в живом процессе через `lldb memory read` (байты
совпадают с сигнатурами). Все принимают L в x0 (паттерн `cbz x0` / `mov x20,x0`).

**lldb breakpoint capture работает** — аттачится к adhoc-процессу, ставит
брейкпоинты на верифицированные адреса, чистый detach, игра выживает.

## Что НЕ сработало (честно)

- **Error-path брейкпоинты не стреляют за 30с на чистой загрузке** — игра
  не дёргает error-пути в логин-шелле. Нужно ловить HOT-функцию, а не error-хелпер.
- **Caller-search провалился**: найденные error-хелперы имеют **ноль прямых
  BL/B-вызовов** в __text (2.7M BL всего просканено, декодер верифицирован) —
  в этом билде они вызываются косвенно (BLR через указатель). Значит найти
  `lua_pcall` как их прямого вызывателя офлайн нельзя.

## Рекомендуемый завершающий шаг (PIVOT 2)

Горячая функция (`lua_pcall` / `lua_pushstring` / `luaV_execute`) не имеет
характерных строк и не вызывается прямо из найденных хелперов. Два варианта:

1. **Ghidra/IDA**: открыть RobloxPlayer, найти `lua_pcall` по структуре
   (пролог + вызов `luaG_errormsg` косвенно + константы `LUA_ERRRUN`/`LUA_ERRMEM`),
   снять сигнатуру, хукнуть → L в x0 при первом же pcall игры (а они идут
   непрерывно).
2. **lldb PC-sampling**: в цикле `process interrupt; register read pc; continue`
   ~100 раз, гистограмма PC → самый горячий кластер = интерпретатор/pcall-путь →
   дизассемблить, верифицировать, брейкпоинт на entry → L. Без Ghidra, но медленнее.

После захвата L: компиляция байткода через собственный компилятор Роблокса
(публичный `luau-compile` НЕсовместим — перемапленные опкоды) + вызов
найденного `luau_load`/`lua_pcall`. Это финальная стадия исполнения.

### Уточнение краша (последний return-only тест)
SIGSEGV pc=0x0, lr→link 0x10027590 — рядом строки "Variant cast failed"
(RBX::Variant). Краш происходит в C++-слое Roblox, НЕ в чистом dispatch.
Dispatch-таблица верифицирована живьём: remapped слоты [84],[125],[135],
[199],[225],[255] заполнены, canonical NULL. Значит resume уходит в
Roblox-обвязку (ScriptContext thread wrapper / Variant конверсия аргументов),
и там падает Variant-cast на нашем потоке.

Гипотеза для проверки: resume(co, from, 0) требует чтобы co был создан
через Roblox-обёртку (ScriptContext::createThread), которая регистрирует
co в scheduler'е; голый lua_newthread даёт co без Roblox-обёртки, и
C++-слой при входе делает Variant-cast параметров планировщика на
NULL-объекте.

Варианты: (а) найти createThread обёртку ScriptContext и звать её;
(б) перехватить ЖИВОЙ вызов lua_resume игры (bp) и подсунуть наш co
вместо игрового; (в) найти где Roblox хранит per-thread RobloxThread*
для lua_State (ExtraSpace? поле?) и проставить.
